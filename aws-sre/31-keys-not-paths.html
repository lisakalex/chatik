Keys, Not Paths

S3 looks like a filesystem in every screenshot and behaves like one in almost no way that matters. This replaces the folder picture with the real one, using the two buckets already defined in your repository.

account 739489595894 us-east-1 verified 2026-09-10 repo aws-sre

The core idea

A bucket is a flat map from one string to a pile of bytes

Everything else — folders, trees, paths — is presentation. This is the return value of upload_avatar in app/services/s3.py, taken apart the same way Module 1 took apart an ARN:

https://prima-tech-challenge-lisakalex.s3.us-east-1.amazonaws.com/avatars/9f2c….png └─────────────┬──────────────┘ └────┬────┘ └───────┬───────┘ bucket name region the key, entire globally unique where bytes live no folder in sight

Three separate facts, and beginners routinely merge them. The bucket name is unique across every AWS account on Earth. The region says which data centres hold the bytes. The key is one flat string — and the slash in it is just a character.

Vocabulary

Three words, used precisely

TermWhat it actually is
bucketA named container in one region. The name is global — prima-tech-challenge-lisakalex is yours and nobody else can ever have it. That is why your Terraform appends a workspace suffix: two environments cannot share one name.
keyThe whole string identifying an object in the bucket. Not a filename, not a path — avatars/9f2c….png is the key, slash included. Maximum 1,024 UTF-8 bytes.
objectThe bytes plus their metadata: content type, size, ETag, storage class, encryption. Up to 5 TB. Written whole, replaced whole — there is no “open the file and seek to byte 400”.

The prefix illusion

There are no directories, and your code proves it

Your uploader never creates a folder, never checks whether one exists, and never fails because one is missing:

# app/services/s3.py key = f"avatars/{uuid.uuid4()}.{extension}" self._client.upload_fileobj(file, self._bucket, key, …)

It builds one string and hands it over. If avatars/ had to exist first, that code would be broken — and it isn't. The console draws a folder icon because it groups keys sharing a prefix up to the next /. That grouping is a display convention, computed on read.

rename a "folder" → copy every object to new keys, delete the originals move an object → same thing: copy, then delete. There is no move. an empty folder → cannot exist. No keys, nothing to group, nothing shown. list "inside" a dir → ListObjectsV2 with Prefix=avatars/ — a string filter

Where the prefix is genuinely load-bearing

Policy and configuration, where it filters by string match. Your lifecycle rule targets prefix = "avatars/"; your IAM policy grants object actions on arn:…:prima-tech-challenge-lisakalex/*. Both are string matching, not directory traversal.

Scope · callback to Module 1, Q3

Global name, regional bytes

You met this exception once already and got it half right: you applied the correct general rule — resources are regional — and S3 broke it. The precise version:

AspectScopeConsequence
the namespaceglobalNames claimed across all of AWS, first come first served. ListBuckets answers from anywhere and returns every bucket you own in every region.
the bytesregionalObjects live in the bucket's region and never silently leave it. That is what makes S3 usable under data-residency rules — and why the region appears in the URL your code returns.

Say it in an interview as: “the namespace is global, the data is regional.” Short, exactly right, and it shows you know S3 is the odd one out.

Design · your repo already contains the argument

Two buckets, opposite choices, both correct

destroyed in the August teardown

aws_s3_bucket.avatars

No versioning. KMS CMK · public access block, all four · lifecycle rules · force_destroy = true

Every upload mints a fresh UUID key, so nothing is ever overwritten — versioning would guard against a danger the design already removed. And it is disposable teaching infrastructure, so it must tear down cleanly.

live right now

aws_s3_bucket.state

Versioning enabled. KMS CMK · public access block, all four · no lifecycle rules · no force_destroy

Holds exactly one hot object — your Terraform state — rewritten on every apply. A corrupt write with no previous version means hand-rebuilding the map of everything you own. Terraform refusing to delete this bucket easily is the point.

The rule underneath

Versioning protects against overwrite and deletion, not against loss of the disk. S3 already handles the disk. Ask “what happens if the current version is wrong?” — if the answer is expensive, turn versioning on and pay for the extra copies.

Proved on your own account

The undo button you have never looked at

list-object-versions on your live state bucket returns your August teardown, recorded in three frames — read bottom to top:

latest size modified version id * 181 2026-08-18 07:14 aEKsFiMJODJ8MS0v… ← current: "resources": [] 1733 2026-08-18 07:13 zG9_rEJhHNQYh0y_… ← mid-destroy 26545 2026-08-18 05:56 KQIXWzVkIdmMmxtd… ← the full stack, 16 resources delete markers: 0

Fetching that 26 KB version with get-object --version-id returns the exact description of everything you owned on 18 August — every resource id and ARN, enough to terraform import your way home. It cost one API call and nothing in dollars.

Three things follow

Old versions were never deleted. IsLatest is just a pointer at the newest one. Overwriting an object in a versioned bucket adds a version and moves the pointer. delete markers: 0 confirms nothing here was deleted, only superseded.

You are billed for 28,459 bytes, not 181. Every version is a stored object. Trivial here; on a bucket where a large file is rewritten nightly it is how people accidentally store the same data three hundred times.

serial went 1 → 3. Terraform's own write counter, with lineage unchanged — that pair is how Terraform detects that two people have diverged, and why the DynamoDB lock table sits beside this bucket.

Durability

Eleven nines, and what it does not mean

S3 Standard is designed for 99.999999999% annual durability. Store ten million objects and you would expect to lose one roughly every ten thousand years. AWS achieves it by replicating across at least three physically separate Availability Zones before acknowledging your write.

What it does not cover, and this is the interview trap: durability is about AWS losing your bytes. It says nothing about you losing them. A bad deploy that deletes the wrong keys, a wrong prefix in a lifecycle rule, credentials in a public repo — all fully durable operations. S3 will preserve the consequences with eleven nines of fidelity.

Availability is a separate, lower number: 99.99% for Standard. Durable means the bytes still exist; available means you can reach them today.

Where the money leaks

A multipart upload that never finishes leaves its uploaded parts in the bucket, billed as storage, invisible in a normal object listing, with nothing to ever delete them. Your abort-incomplete-multipart-uploads rule at 7 days exists for exactly this. It is the most common silent S3 bill in the wild, and you fixed it before it happened.

Hands-on · ~10 minutes · costs nothing

Run it against your own bucket

Warm the session first — aws sts get-caller-identity --profile admin in your own terminal — then read the output rather than skimming it.

1

Confirm the global listing

aws s3 ls --profile admin — no region flag, yet it answers. That is the global half.

2

Find the region of the bytes

aws s3api get-bucket-location --bucket prima-tech-challenge-lisakalex-tfstate --profile admin — returns null, which means us-east-1. That region predates the concept of a location constraint, so it is encoded as the absence of one.

3

Read a real key as a string

aws s3 ls s3://prima-tech-challenge-lisakalex-tfstate --recursive --profile admin — senior-sre-tech-challenge/terraform.tfstate looks like a folder and a file. It is 43 characters.

4

Watch versioning work

aws s3api list-object-versions --bucket prima-tech-challenge-lisakalex-tfstate --profile admin — every past state file, each with its own version id.

5

Create a fake folder without creating one

Upload any small file to key demo/a/b/c.txt. No directory was made, because there is no such thing. Then delete it — and in a versioned bucket, watch delete markers go from 0 to 1 while the object stays recoverable.

Check yourself

Four questions

Same rules as the Module 2 check: your own words, closed book, “not sure” is a real answer. Hints only inside.

1. A colleague says "I'll just rename the avatars/ folder to photos/, it's one click in the console." What actually happens, and what would it cost on two million objects?

There is no rename operation in the API. Work out what the console must therefore do on your behalf, then count the requests.

2. The state bucket has versioning on; the avatars bucket does not. Give the reason for each — and name a disaster versioning would not have saved the state bucket from.

The first half is on this page. For the second, ask what versioning protects and what it does not: something that removes the bucket, or the key that decrypts it.

3. A teammate wants to name a bucket backups. Predict the error, and say which of the three words — bucket, key, object — is the reason.

One of the three has a scope the other two do not. The error message says so out loud.

4. Someone claims "S3 is eleven nines durable, so we don't need backups." Where exactly is that wrong? Name one failure it does nothing about.

Eleven nines describes one party's failure mode. Ask whose — and who else is in a position to destroy the data.
