How Role Assumption Works

You asked how “a role can be assumed” actually works. It's two permission checks, at two different moments, against two different policies — and once you can see that, the whole two-policy structure stops being arbitrary.

The mechanism

Two checks, two moments

Step by step

What actually happens

1

You call sts:AssumeRole

An ordinary AWS API call — a signed HTTPS POST to sts.amazonaws.com, exactly as in Module 1. You sign it with the credentials you already have: your permanent AKIA key. You name the role you want by its ARN.

2

STS reads the role's trust policy

The doorman looks at the guest list attached to the hat. Is lisakalex named on it? Is the account? The service? If not, you get AccessDenied and nothing else happens. This check runs exactly once.

3

STS mints temporary credentials

You get back three strings, not two: an access key starting ASIA, a secret, and a session token. The token is what marks them as temporary; every request must carry it. They come with a hard expiry — typically an hour.

4

You call AWS with the new credentials

Same SigV4 signing as before, just a different key. But now AWS sees the caller as the role, not as lisakalex. Your own permissions are gone for the duration — you have exactly what the role has, no more.

5

The service reads the role's permissions policy

S3 asks: may this role read this object? This check runs on every single call — there's no cached verdict. Then the credentials expire and you're back to being yourself.

Why the two-policy design now makes sense

They answer different questions, are evaluated by different services, at different times. The trust policy is a door: STS checks it once, on entry. The permissions policy is a set of powers: every service re-checks it, every time you use them.

It also explains the asymmetry from Lesson 2.1. A bad permissions policy shows up immediately, because it's checked constantly. A bad trust policy is checked once, silently, at the door — and if it lets the wrong person in, everything afterwards looks completely normal.

Made concrete

What it looks like on the command line

# who am I right now? $ aws sts get-caller-identity Arn: arn:aws:iam::739489595894:user/lisakalex # put on the hat — this is step 1 $ aws sts assume-role \ --role-arn arn:aws:iam::739489595894:role/demo-read-only \ --role-session-name learning # step 3 — three strings come back, not two { "Credentials": { "AccessKeyId": "ASIA2YLIDYH3XXXXXXXX", "SecretAccessKey": "…", "SessionToken": "IQoJb3JpZ2luX2Vj…", ← the extra one "Expiration": "2026-08-30T12:34:56Z" ← the hard deadline } } # step 4 — same command, wearing the hat $ AWS_ACCESS_KEY_ID=ASIA… AWS_SECRET_ACCESS_KEY=… AWS_SESSION_TOKEN=… \ aws sts get-caller-identity Arn: arn:aws:sts::739489595894:assumed-role/demo-read-only/learning

Look at how the ARN changes. You stop being user/lisakalex and become assumed-role/demo-read-only/learning. That's not cosmetic — it's what CloudTrail records, so an auditor can see both which role acted and which session did it. The session name you chose is preserved in the identity.

The session token is not optional

Temporary credentials need all three values. Supply just the key and secret and you get InvalidClientTokenId — a confusing error that sends people hunting for a typo in their key. It's the single most common mistake when first working with assumed roles.

The part that matters in production

Machines do this without anyone typing

Everything above showed you assuming a role using a key you already had. But the real value is that a machine can do it with nothing stored on disk. What changes is only step 1 — what the caller uses to prove who it is:

CallerProves identity withRest of the flow
You, at a terminalYour AKIA keyIdentical from step 2 onward — trust policy check, temporary credentials, permissions policy on every call.
EC2 instanceInstance identity from 169.254.169.254, reachable only from that instance
Kubernetes podA signed ServiceAccount token on its filesystem (IRSA)
GitHub ActionsAn OIDC token GitHub mints for that one workflow run

That's the answer to your Lesson 2.1 insight, “no keys need to be present on the client.” The client proves who it is with something it is rather than something it stores, then follows the identical assume-role path. The trust policy is what decides which of these callers is allowed in — which is why it's the document worth being careful about.
