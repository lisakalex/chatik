The Missing Claim

Your repository contains two OIDC trust policies. One is written the way AWS documents it. The other is missing a condition. Both sit in terraform/, and by the end of this page you should be able to say which one, and what an attacker does with the gap.

This is also the full answer to the question you kept pushing on in 2.2 — how do you get access without a key? — taken down to the wire.

The problem

A pod has no access key. It has a signed statement.

A container in Kubernetes needs to write to S3. The old answer was to bake an AKIA key into an environment variable or a secret, and then own that secret forever. The modern answer removes the secret entirely, and the mechanism is worth learning exactly, because every federated login in AWS works this way: GitHub Actions, GitLab, CircleCI, Okta, Google, EKS. Same machinery, different issuer.

The cluster mints a short-lived JWT — a small JSON document signed with the cluster's private key — and mounts it into the pod as a file. That file is not an AWS credential. It is a statement about who this pod is, signed by something AWS has been told to trust.

The answer to "access without a key"

The pod holds no shared secret. It holds a document that only the cluster could have signed, and AWS verifies that with a public key anyone in the world may download. That is the entire trick — and it is why the file inside the pod expires in minutes and is useless outside this exchange.

What is in the token

Four claims, and two of them are the security boundary

Decoded, the JWT the kubelet mounts looks roughly like this:

{ "iss": "https://oidc.eks.us-east-1.amazonaws.com/id/EXAMPLE", // who signed it "sub": "system:serviceaccount:default:prima-app-sa", // who it is about "aud": "sts.amazonaws.com", // who it is FOR "exp": 1757068800 // dies in minutes }
ClaimWhat it meansChecked by
issWhich issuer signed this, and therefore which public keys STS goes and fetches.The Federated principal
subSubject — which ServiceAccount, in which namespace. The identity.A Condition you write
audAudience — which service this token was minted to be shown to.A Condition you write
expExpiry. Minutes, not hours.STS, automatically

sub and aud answer different questions

sub is the photo on a badge — it proves who you are. aud is the building name printed on it — which door this badge was issued for. A real badge, with your real face, issued for a different building, should not open this one.

Your code · find the difference

Two trust policies from this repository

Both grant sts:AssumeRoleWithWebIdentity. Both name a Federated principal. Both constrain sub. Read the two Condition blocks against each other before you open the answer.

iam-github-oidc.tf

complete
Condition = { StringEquals = { "...githubusercontent.com:aud" = "sts.amazonaws.com" } StringLike = { "...githubusercontent.com:sub" = [ "repo:owner@ID/aws-sre@ID: ref:refs/heads/main", "repo:owner@ID/aws-sre@ID: environment:production", ] } }

main.tf · app_role

incomplete
Condition = { StringEquals = { "${eks_oidc}:sub" = "system:serviceaccount:default:prima-app-sa" } } // nothing here reads :aud
What is missing — and does it actually matter?

The IRSA role never checks aud. It verifies which ServiceAccount the token is about, and not which service the token was minted for.

Be precise about the risk, because the sloppy version of this answer is wrong in an interview. It is not "any workload can assume the role" — the sub condition still pins it to prima-app-sa in the default namespace. The real exposure is audience confusion.

Kubernetes lets that same ServiceAccount mint tokens for other audiences through the TokenRequest API — a service mesh, a vault, an internal API, an outbound webhook. Those tokens carry the same sub and a different aud. Any service you hand one to is now holding something AWS will accept as proof of being your application.

The honest caveat: a second gate you cannot see from here

When an OIDC provider is registered in IAM it carries a client_id_list, and STS rejects tokens whose audience is not on it. The GitHub provider in this repo sets it to ["sts.amazonaws.com"] — line 7 of iam-github-oidc.tf. But the EKS provider is not defined in this repository at all: eks_oidc is only a string variable, so that provider was registered somewhere you cannot review. You have no way to prove its audience list is narrow. The trust-policy condition is the gate you own, in the file you control, and it is the one a reviewer will look for.

The fix

One condition, one line

Condition = { StringEquals = { "${var.eks_oidc}:aud" = "sts.amazonaws.com" "${var.eks_oidc}:sub" = "system:serviceaccount:default:prima-app-sa" } }

Both keys go inside the same StringEquals block, and multiple condition keys in one block are ANDed — every one must hold. Worth carrying past this lesson: condition keys are AND, but multiple values listed for a single key are OR. That is exactly why the GitHub policy can accept two different sub formats while still requiring the audience.

The version that is genuinely catastrophic

Notice what the app role gets right: sub is matched with StringEquals against an exact string. The failure you will meet in real codebases is StringLike with a wildcard — "system:serviceaccount:*" — which hands the role to every pod in every namespace of the cluster, including anything an attacker manages to deploy. A wildcard inside a trust policy deserves a hard stop in code review, every time.

Transferable

Reading any trust policy in about a minute

  • Who is the Principal? An account, a service, or a Federated provider. If it is "*", stop reading and fix it.
  • Which action? sts:AssumeRole means the caller already holds AWS credentials. sts:AssumeRoleWithWebIdentity means an outside identity provider is involved — so the conditions are carrying all the weight.
  • Is there a Condition at all? A federated trust policy with no conditions trusts every identity that provider can issue. For GitHub, that means every repository on GitHub.
  • Does it constrain both who and for-what? sub and aud. A missing sub is a catastrophe; a missing aud is a gap.
  • Any wildcards? StringLike with a * in the middle of a sub is where breaches come from.

Check yourself

Three questions

1. A colleague says "the aud condition is pointless, the OIDC provider already restricts the audience." Are they right?

Partly — and the interesting half of the answer is not about correctness. Think about who owns each of the two gates, and which one you can actually see from this repository.

2. Why is a stolen JWT less dangerous than a stolen AKIA key, even though both can be turned into AWS credentials?

Look at the exp claim first, then at what else has to be true for the exchange to work at all.

3. The GitHub role pins sub using numeric IDs rather than plain names. What attack do those numbers stop?

Names on GitHub are not permanent. Ask what happens to a trust policy written against a name after the account holding that name goes away.
