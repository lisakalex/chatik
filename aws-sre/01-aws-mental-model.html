The AWS Mental Model

One signed API, three coordinates, and the exceptions that catch people out. Everything on this page was verified against a live account rather than quoted from documentation.

account 739489595894 us-east-1 verified 2026-08-29 repo aws-sre

The core idea

AWS is one API. Everything else is a client.

Running aws sts get-caller-identity produces exactly this on the wire — an authenticated HTTPS POST and nothing more:

POST / HTTP/1.1 Host: sts.us-east-1.amazonaws.com Content-Type: application/x-www-form-urlencoded X-Amz-Date: 20260829T033611Z Authorization: AWS4-HMAC-SHA256 Credential=AKIA2YLI…LYFS/20260829/us-east-1/sts/aws4_request, SignedHeaders=content-type;host;x-amz-date, Signature=23b05ef0f714… Action=GetCallerIdentity&Version=2011-06-15

Creating a server, deleting a database, uploading a file — all of it is this same shape, sent to <service>.<region>.amazonaws.com. There is no other channel into AWS.

ClientWhat it actually is
ConsoleA JavaScript app making these calls for you
AWS CLIThe same calls from a terminal
SDK (boto3)The same calls from your code — app/services/s3.py
TerraformDiffs your .tf files against reality, then makes these calls

The consequence people miss

The console has no privileged back door, because the API is the internals. Console and CLI used by the same identity can do exactly the same set of things — both are bounded by that identity's IAM policy. The difference is surface area exposed, not authority granted.

“Lock down the CLI, let everyone use the console, it's safer” is therefore false, and it causes real breaches. Permissions are the control. The tool is not.

Authentication

SigV4: the secret never leaves your machine

The access key ID is public-ish, like a username. The signature is an HMAC computed over the request itself — method, host, headers, body, timestamp — using your secret key. So:

Get this the right way round

The secret key is not the thing being hashed. It is the key you hash with. Message = the request. Key = your secret. Output = the signature. Because the scope pins a date, region, and service, a captured signature cannot be replayed against another service or on another day.

Proof, from three real calls made seconds apart:

# identical request, same second — identical signature (deterministic) call 1 …/us-east-1/sts/aws4_request SignedHeaders=content-type;host;x-amz-date Signature=fda774725b127aee call 2 …/us-east-1/sts/aws4_request SignedHeaders=content-type;host;x-amz-date Signature=fda774725b127aee # different service — different scope, different signed headers, different signature call 3 …/us-east-1/s3/aws4_request SignedHeaders=host;x-amz-content-sha256;x-amz-date Signature=922c65f2b74e9adf

Note that S3 adds x-amz-content-sha256 — it signs a hash of the request body too, so an upload cannot be tampered with in flight.

Where the SSH analogy breaks

SSH — asymmetric

You keep the private key; the server holds only your public key. The server can verify your signature but cannot produce one. A leak of the server's key database is harmless.

SigV4 — symmetric

There is no keypair. AWS holds a copy of your secret. Both sides compute the same HMAC and compare. AWS could sign as you.

Three consequences of that

1. You can only ever see a secret key once, at creation. Lose it and you rotate, you don't recover.

2. A leaked secret key is total account compromise — no public/private split to save you. Keys committed to public repos get found in minutes; miners follow.

3. Long-lived secrets are the thing to engineer away. That is what OIDC and IRSA exist for.

PrefixCredential typeLifetime
AKIAIAM user access keyForever, until manually deleted
ASIATemporary credentials from STSMinutes to hours, then dead

Memorise these two prefixes. Every AWS credential announces its own type in its first four characters.

Addressing

Three coordinates: account, region, AZ

Account

Blast radius and bill

Resources in one account are invisible to another unless explicitly granted. Companies run many accounts — prod, staging, dev — precisely so a mistake in one cannot reach another.

Region

Geography

A physical cluster of datacentres. Regions are near-independent: different endpoints, separate resources. Chosen on latency, data-residency law, price, and service availability.

Availability Zone

Failure domain

Independent power and cooling, linked by private fibre. How you survive a datacentre fire without going multi-region.

Latency is a design input, not a footnote

Measured from a UK machine to each region's S3 endpoint — the argument for choosing a region that no lawyer needs to be involved in:

RegionTCP connectTLS handshake
us-east-1126 ms 242 ms
eu-south-1 (Milan)71 ms 118 ms
eu-west-1 (Ireland)49 ms 92 ms
eu-central-1 (Frankfurt)43 ms 83 ms

Roughly 2–3× the round trip — and that is per round trip. One HTTPS request already needs several, before your app makes its own calls to S3 and DynamoDB.

GDPR does not say what most people think

GDPR (General Data Protection Regulation — data protection, not “digital rights”) does not require EU personal data to stay in the EU. Transfer to the US is lawful with Standard Contractual Clauses or the EU–US Data Privacy Framework, which AWS is certified under.

The honest argument for staying in-region: transfers are legal but carry a compliance workstream — Transfer Impact Assessments, SCC paperwork — and standing legal risk. That ground has already shifted twice, with Safe Harbour struck down in 2015 and Privacy Shield in 2020.

For a regulated sector the stronger levers are elsewhere: DORA, EIOPA cloud-outsourcing guidelines, and the national supervisor (IVASS for Italian insurance).

“Global” means one control plane, not a replicated one

Those services' control planes physically run in us-east-1. When us-east-1 has a bad day, IAM changes stall worldwide — even for companies running entirely in Europe. The October 2025 outage began as a DNS failure in front of DynamoDB in us-east-1 and cascaded far beyond it for exactly this reason.

Related: IAM is eventually consistent. A role you just created may not be usable for a few seconds. Terraform hits this constantly — an apply fails with “role does not exist” on a role it created moments earlier, then succeeds on retry.

The exception

S3 breaks the region rule

The general rule — look in the wrong region and you see nothing — holds for EC2, DynamoDB, Lambda, RDS, VPC. It is the number one cause of “my resource disappeared.” S3 splits the difference in a way nothing else does:

Aspect of S3Scope
Bucket nameGlobally unique — across every AWS account on Earth
Bucket dataRegional — objects physically live in one region
ListBucketsGlobal — returns every bucket in every region
# same account, same credentials, same moment S3 buckets region=us-east-1 → prima-tech-challenge-lisakalex-tfstate S3 buckets region=eu-west-1 → prima-tech-challenge-lisakalex-tfstate ← still visible S3 buckets region=ap-southeast-2 → prima-tech-challenge-lisakalex-tfstate ← still visible DynamoDB region=us-east-1 → prima-tech-challenge-lisakalex-tfstate-lock DynamoDB region=eu-west-1 → (nothing) ← invisible

Why the namespace is global: buckets are addressable as DNS hostnames, and DNS is globally unique.

https://prima-tech-challenge-lisakalex-tfstate.s3.amazonaws.com/… └─────── the bucket name is a subdomain ───────┘ # AWS says so itself: BucketAlreadyExists: The requested bucket name is not available. The bucket namespace is shared by all users of the system.

This is why real bucket names look like prima-tech-challenge-lisakalex-tfstate — org prefix, purpose, account suffix. Not verbosity for its own sake; avatars was claimed fifteen years ago. It is also why names must be lowercase and DNS-safe.

Two S3 warts that bite in code

get-bucket-location returns null for us-east-1. It was the original region, predating the concept, so it has no location constraint string. Code doing if location == "us-east-1" breaks.

Region is not an access barrier for S3. Reading a bucket while configured for another region just works — the SDK follows the redirect. Region governs where bytes sit, which matters for latency, cost, and residency; not for permission.

Retain these

The six keepers

AWS is one signed HTTPS API. Console, CLI, SDK, and Terraform are four clients of it. What you may do comes from IAM, not from which tool you picked.

SigV4 never transmits your secret. The secret is the key you HMAC with; the message is the request. Scoped to date, region, and service so it cannot be replayed elsewhere.

It is symmetric, unlike SSH. AWS holds a copy. Hence: you see it once, a leak is total compromise, short-lived credentials are the goal. AKIA permanent, ASIA temporary.

Account → Region → AZ. Account is blast radius and bill. Region is geography. AZ is failure domain.

Empty region in an ARN means a global service. IAM, Route 53, CloudFront, Organizations, WAF, Billing — control planes all in us-east-1, which is why a bad day there is felt worldwide.

S3 is the exception to region-scoping. Global name, global listing, regional data.

Revision

Test yourself

Answer out loud before opening. Recalling is what moves this into long-term memory; re-reading does not.

A colleague says the S3 console has special access to AWS internals the CLI doesn't. Are they right?

No. The console is a JavaScript app making the same signed API calls. There are no internals behind the API — the API is the internals.

Stronger point: the same identity has the identical permitted action set in both. The console merely exposes a curated subset of what the API offers. Surface area, not authority.

Was your secret access key sent to AWS? What was sent instead?

No. An HMAC signature over the request was sent — computed using the secret as the key. Also sent: the access key ID, so AWS knows which secret to look up.

But unlike SSH, AWS does hold a copy of that secret. Symmetric, not asymmetric.

You create a bucket in us-east-1. A teammate in the eu-west-1 console can't find it. Broken?

Neither — they can see it. ListBuckets is global and the S3 console's bucket list is region-agnostic, showing all buckets with a Region column.

For almost anything else — EC2, DynamoDB, Lambda — “check your region” would be the right answer.

Why does an IAM ARN have an empty region field when a KMS ARN doesn't?

IAM is global — one endpoint, iam.amazonaws.com, for the whole account. KMS is regional, one endpoint per region, and a key exists in exactly one of them.

Practical consequence: a KMS key cannot cross regions. Move an encrypted bucket to another region and you need a new key and a re-encrypt.

Italian insurer, running in us-east-1. Argue both sides.

Move: latency is 2–3× better from Europe, and sector rules — DORA, EIOPA, IVASS — push harder on residency than GDPR does.

Stay: us-east-1 is cheapest and gets features first. Quantify it: the S3 storage gap is a few percent, with real deltas in compute, NAT, and data transfer.

The senior answer: it depends which system you mean. For a demo project with no personal data, GDPR doesn't engage and latency is theoretical, so staying is fine if documented. For real production, the decision flips. Recognising that the question has two different answers is the thing being tested — as is knowing that us-east-1 is also AWS's least reliable region.
