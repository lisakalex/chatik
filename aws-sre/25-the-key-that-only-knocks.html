The Key That Only Knocks

Right now, one readable file on your laptop is your entire AWS account. By the end of this lesson that same file will be able to do exactly one thing — knock on a door that does not open without your phone.

This is the capstone of Module 2: everything from 2.1 to 2.4 aimed at the credential you actually use every day.

The situation

What an attacker gets from one cat

$ ls -l ~/.aws/credentials -rw------- 1 al al 116 Jul 21 16:07 ~/.aws/credentials $ cat ~/.aws/credentials [default] aws_access_key_id = AKIA2YLI**** aws_secret_access_key = 5Cuk****
FactYour account today
Permissions on that keyAdministratorAccess, no conditions
Age46 days, never rotated
Stored asPlaintext. Mode 0600 is the only thing guarding it
MFA on the userYes — and irrelevant to this file
What it can doEverything. Delete the account's data, mint new users, run up a bill

No exploit is required

Nobody has to break anything to use this. It is a file, readable by your user, and so is readable by every process you run: a postinstall script in some npm package, a compromised editor extension, a curl-pipe-bash you trusted, an old laptop backup, a synced folder. Mode 0600 stops other people on the machine. It does not stop code running as you.

And per lesson 2.1, MFA does nothing here. There is no sign-in in an API call. Your phone is never consulted.

The design

Take B. Not because A is wrong, but because A protects you with a rule that has to be written perfectly — and the next section shows how easy that is to get wrong. B protects you by not granting the permission in the first place. A missing permission cannot be misconfigured.

It is also the shape of every real environment you will work in: humans hold something that can only assume roles, and the roles hold the power. AWS IAM Identity Center is this pattern with a login page in front of it.

The subtlety · this is an interview question

Bool vs BoolIfExists

aws:MultiFactorAuthPresent has three states, not two — and the third is the one that catches people:

Request made withKey value
Temporary credentials minted with an MFA codetrue
Temporary credentials minted without onefalse
A long-term AKIA keyabsent — the key is not in the request at all

Now watch what that does to a Deny written the obvious way:

// BROKEN - the exact case you are trying to block sails straight through { "Effect": "Deny", "Action": "*", "Resource": "*", "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "false" } } } // CORRECT - "false, OR not present at all" { "Effect": "Deny", "Action": "*", "Resource": "*", "Condition": { "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" } } }

With plain Bool, a raw AKIA request carries no such key, so the condition never matches, so the Deny never fires. You would have written a policy that blocks exactly the credentials that were already safe and permits the ones you were afraid of. BoolIfExists means "if the key is there compare it; if it is absent, count that as a match".

Why your 2.2 role was right anyway

Your learning-mfa-demo trust policy uses plain Bool with "true", and that is correct — because it is an Allow. An absent key fails to match, so the Allow does not apply, and per lesson 2.3 you land on implicit deny. Safe by default.

The rule: Bool + true in an Allow is safe. Bool + false in a Deny is a hole. A positive test fails closed; a negative test fails open.

The build

Six steps, in this order

Step 0 — prove the escape hatch before you touch anything

You are about to remove your own admin rights from the only key you have. If it goes wrong, the way back is the root user, which can always repair IAM. Your account is in good shape for this — root MFA is enabled and root has no access keys — but do not take that on trust. Log into the console as root, right now, in a browser, and confirm the MFA prompt works. Then log out. Do not continue until you have.

1. Create the role. Same trust policy shape as the one you already built in 2.2, with AdministratorAccess attached instead of one S3 action.

# trust: only this user, only with MFA { "Version": "2012-10-17", "Statement": [{ "Effect": "Allow", "Principal": { "AWS": "arn:aws:iam::739489595894:user/lisakalex" }, "Action": "sts:AssumeRole", "Condition": { "Bool": { "aws:MultiFactorAuthPresent": "true" } } }] }

2. Add the profile to ~/.aws/config. This is what makes the whole thing survivable day to day — the CLI prompts for the code, then caches the temporary credentials until they expire.

[profile admin] role_arn = arn:aws:iam::739489595894:role/admin source_profile = default mfa_serial = arn:aws:iam::739489595894:mfa/al-iphone duration_seconds = 3600

3. Test it while you are still admin — this is the point of doing it in this order.

$ aws sts get-caller-identity --profile admin Enter MFA code for arn:aws:iam::739489595894:mfa/al-iphone: ______ "Arn": "arn:aws:iam::739489595894:assumed-role/admin/botocore-session-…"

4. Swap the user's permissions — detach AdministratorAccess, attach a policy that permits one action on one resource. Do this from the admin role session, so that session stays alive as a second way back.

{ "Version": "2012-10-17", "Statement": [{ "Sid": "KnockOnly", "Effect": "Allow", "Action": "sts:AssumeRole", "Resource": "arn:aws:iam::739489595894:role/admin" }] }

5. Prove the key is now worthless on its own.

$ aws s3 ls # naked AKIA key AccessDenied $ aws s3 ls --profile admin # same key + your phone 2026-08-18 … tfstate bucket

6. Rotate the key. It is 46 days old and it has been sitting in plaintext the whole time. It is far less valuable now, which is exactly why this is the right moment — do it calmly rather than during an incident.

Consequences

What breaks, and what does not

unaffected

GitHub Actions

Your pipeline authenticates by OIDC and assumes its own role — it never touches this user or this key. Nothing to change. That is lesson 2.4 paying for itself.

needs the profile

Terraform, Docker, ECR

Anything you run locally now needs AWS_PROFILE=admin in the environment, including terraform plan against the S3 backend and aws ecr get-login-password.

new habit

One code per hour

The CLI caches the session in ~/.aws/cli/cache/, so you type six digits at most once an hour, not once a command.

Honesty

What this does not fix

  • The cache is plaintext too. While a session is live, ~/.aws/cli/cache/ holds working admin credentials, readable by anything running as you. The difference is that they expire — you have narrowed an unlimited window to about an hour.
  • Malware that waits. Code running as you can simply sit there until you type your next code, then ride the session. MFA raises the cost and forces the attacker to be present; it does not make the machine trustworthy.
  • The key still identifies you. sts:GetCallerIdentity needs no permission at all, so a thief still learns your account ID and username. Minor, but true.
  • Root is now load-bearing. You have made root your recovery path, so its MFA device matters more than it did yesterday. Know where it is.

The honest summary: you have converted "one file, forever, everything" into "one file plus a physical device you hold, for an hour at a time". That is not perfect security. It is the difference between a leak being a catastrophe and a leak being a nuisance.

Check yourself

Three questions

1. Why did step 4 come after step 3, and not before?

Ask what you would still have been able to do if the role or the profile had been wrong — in each of the two orderings.

2. You write the Deny policy from design A using Bool instead of BoolIfExists, and test it with credentials from get-session-token. It appears to work. Why is that test worthless?

Which of the three states did your test actually exercise — and which one was the whole point?

3. Your teammate says "just encrypt ~/.aws/credentials instead, it is simpler." What is wrong with that?

Follow the sequence through: the AWS CLI has to send a usable secret. Where does the plaintext have to exist, and who can read it there?
